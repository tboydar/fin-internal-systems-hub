# ADR 0003：假資料只有一個來源，畫面上的數字都是算出來的

- 狀態：已採用
- 日期：2026-11-24

## 背景

Demo 最容易穿幫的地方，是兩頁的數字對不起來：總覽說 4 條介面要注意，點進去卻是 5 條；
廠商頁寫 SLA 96%，工單表數一數卻不是。看的人只要發現一次，就不會相信其他的數字。

## 決定

- 資料只有一個來源：`buildInitialState()`（`src/mock/index.ts`）。有型別，用固定種子，每次建置結果相同。
- 原始資料只存「事實」：工單的開單與解決時間、任務的人天、文件的上次檢視日、每一次執行的結果。
- 畫面上的數字一律由事實推導，不另外存：
  - SLA 達成率、交付準時率、驗收退件率、計罰：`src/core/sla.ts`
  - 介面與系統的健康狀態、影響範圍：`src/core/selectors.ts`
  - 負載、bus factor、文件是否過期、凍結期、等我決定的事：`src/core/derive.ts`
  - 各角色看到的句子：`src/core/narrative.ts`
- 日期一律用台北時間，工作日依人事行政總處的辦公日曆表避開國定假日（`src/core/date.ts`）。

## 代價

要「調」一個數字不能直接改它，得去改背後的資料。例如想讓某家廠商的達成率低一點，要去調它的逾時機率，再看算出來是多少。

## 怎麼守住

`tests/unit/` 有幾類測試：

- 參照都對得上；介面的廠商等於所屬系統的廠商。
- 改一張工單，達成率就跟著變（證明不是寫死的）。
- 總覽上每個數字等於來源的列數；瀏覽器測試再點進去數一次。
- 不全綠也不全紅：有一家廠商好、一家普通；有幾份文件過期；有一條介面長期不穩。
- 已核准的變更不落在凍結期。這條測試在寫的時候就抓到一筆排錯的資料。
